# Concepts and likely interview questions

1. **Why use integer minor units?** Decimal money such as 0.1 is not always exactly representable as a binary floating-point number. Integer piastres keep supported operations exact. Here 100 piastres is EGP 1; validation bounds each entry, and the service guards total safe-integer overflow.
2. **Why derive the balance?** A second mutable balance can drift from history if one write fails or is forgotten. This small demo derives the value from its source records. A much larger ledger might use carefully maintained summaries and reconciliation.
3. **What race would happen without locking?** With a 100-pound balance, two requests might each read 100 and approve separate 70-pound payments, producing an overpayment. Both service calls lock the same student row, so the second waits, reads 30 after the first commits, and rejects 70.
4. **Why lock Student rather than existing payments?** A student can have no payments yet. The stable parent row exists before ledger records and gives all writers a shared lock target.
5. **Why Read Committed for writes?** After waiting for a row lock, subsequent queries see newly committed records. Repeatable Read would retain an older snapshot; explicit locking and isolation choices must agree. All write paths need the same locking convention.
6. **Why Repeatable Read for the fee response?** Prisma may issue multiple queries for related records. One snapshot ensures history and derived totals describe the same database state while other requests write.
7. **Why a database unique constraint as well as a lookup?** Two transactions for different students take different row locks. Both can pass a lookup for a reference that does not exist yet. The unique index permits just one insert. The API maps the losing insert to 409.
8. **Does a duplicate reference mean idempotent success?** No. This API returns 409. The client retrieves the ledger and checks whether the original payment succeeded. It does not silently treat potentially different payloads as equivalent.
9. **What does a transaction guarantee?** The balance check and insertion either complete together or roll back together. Locks remain held until the transaction ends. A rejected payment leaves no partial payment entry.
10. **Authentication versus authorization?** Authentication identifies the staff user from a verified token. Authorization checks whether the current role permits a requested action. A valid reader token can still receive 403.
11. **Why bcrypt and why not encrypt passwords?** Hashing verifies a password without recovering it. Bcrypt uses salts and a configurable work factor. An environment secret signs tokens; password hashing and token signing serve different purposes.
12. **Why constrain JWT verification?** Fixed HS256, issuer, audience, signature, and expiry checks prevent accepting tokens outside the intended contract. The account is loaded again to apply its current role. There is no refresh/revocation system in this scope.
13. **Where does validation belong?** Zod parses HTTP inputs, rejects unknown fields, and provides useful error details. Database constraints provide a second boundary for positivity, uniqueness, and relations. Business rules such as overpayment live in the fee service.
14. **Why 400, 401, 403, 404, and 409?** Respectively: invalid request, failed identity verification, insufficient permission, missing resource, and conflict with current state. Unexpected errors are 500 without internal details.
15. **Why PostgreSQL tests instead of mocks or SQLite?** Row locks, transaction isolation, and unique-constraint races depend on real database behavior. HTTP integration tests verify the actual application path. Pure calculation checks complement them.
16. **How are tests kept safe?** The runner allocates a brand-new randomly named database and tracks whether creation succeeded before attempting to drop that exact database. It never resets the configured user database.
17. **What should change for production?** Add operational security, TLS, secret management, backup/recovery, distributed throttling, redacted observability, staff account lifecycle, and carefully designed correction/reversal workflows. Keep an audit trail instead of editing financial history.
18. **Why this structure and scope?** Routes, controllers, and services keep HTTP concerns apart from business behavior while staying small enough to understand. The assignment asks for a complete core workflow and supporting features within a strict deadline.

Practice explaining the transaction using the 100/70/70 example. Read `recordPayment` line by line until you can describe the lock, reference check, balance calculation, insert, and rollback without memorizing a script.
